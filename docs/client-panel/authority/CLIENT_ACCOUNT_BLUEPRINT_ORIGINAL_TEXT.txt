0.1 Core product boundary
Permanent Separation Rule
The iDigitalRoot Client Account, the Client Website Admin/CMS, and the iDigitalRoot Internal Admin/Operations Dashboard are three distinct applications. The client account must never drift into a general website CMS or hosting control panel.
0.2 Core philosophy
The client manages the relationship with iDigitalRoot, services, websites, renewals, project approvals, social links, and support from one account.
The client manages day-to-day website content inside each website’s own CMS.
iDigitalRoot staff manage internal operations, project execution, infrastructure, deployment, billing control, security, and audits in the future Admin Dashboard.
The core client account remains useful even if every optional future external integration disappears.
1. Product Definition
The Client Account is the customer-facing operating center for all iDigitalRoot relationships and Digital Roots. It is not a website builder, hosting panel, analytics clone, or AI assistant.
Client Experience Promise
One account. All websites. Clear status. Clear actions. Clear renewals. Direct access to each website’s CMS when needed.
1.1 Primary questions the dashboard must answer
What websites and services do I currently have?
Does anything require my attention?
What is happening with a website that is being built?
How do I open a live website’s Admin/CMS?
When does each subscription, domain, or service renew?
How do I request a major change or support?
What services are available from iDigitalRoot?
1.2 Non-goals
Editing normal website content.
Managing website users, products, posts, categories, or media.
Duplicating website-specific analytics.
Exposing cPanel/Plesk/server administration.
Providing raw DNS editing in the normal client experience.
Providing Git, deployments, databases, logs, API secrets, or infrastructure controls.
Providing an AI chatbot.
Providing a generic cloud file vault.
2. Application Boundaries & Data Separation
PUBLIC iDIGITALROOT WEBSITE        |        viDIGITALROOT CLIENT ACCOUNT   |          |          |   |          |          +--> Website C Admin/CMS   |          +-------------> Website B Admin/CMS   +------------------------> Website A Admin/CMSINTERNAL iDIGITALROOT ADMIN / OPERATIONS        (separate staff application)

2.1 Data separation rule
Website CMS data stays in the website/CMS environment. iDigitalRoot account data stays in the iDigitalRoot platform. Communication is limited to explicitly approved contracts such as secure SSO, service-status checks, or later narrowly defined integrations.
2.2 No general data synchronization
No automatic transfer of articles, products, website users, media libraries, or CMS content into iDigitalRoot.
No dependence on a website CMS database for the Client Account to function.
No shared credential database between the Client Account and client CMS.
Future APIs must be individually justified, costed, permissioned, and versioned.

17. One-Click Website Admin SSO
A logged-in iDigitalRoot client can click Open Website Admin and enter the selected website’s separate CMS without retyping CMS credentials. Direct access to the CMS URL remains possible and uses the CMS’s normal authentication.
17.1 Required SSO flow
Authenticated iDigitalRoot user  -> selects Website A  -> clicks Open Website Admin  -> server authorizes ownership and entitlement  -> creates signed, short-lived, single-use SSO ticket  -> browser redirects to Website A CMS SSO endpoint  -> CMS validates issuer, signature, audience, expiry, nonce, website/user scope  -> CMS creates local session  -> ticket marked used / becomes invalid

17.2 Ticket properties
Signed and tamper-evident
Single-use
Very short expiration
Audience restricted to one CMS/site
Bound to specific client user and website
Contains unique nonce/ticket identifier
Contains minimal permission scope
Never contains a reusable password
Never appears in long-lived logs or analytics
Every issuance and consumption is audit logged
17.3 Explicit prohibitions
Never put username/password in URL parameters.
Never store reusable CMS credentials in browser storage for SSO convenience.
A ticket for Website A can never authenticate Website B.
SSO must fail closed on validation error, expiration, replay, or mismatched audience.

29. Input, Application & Tenant Security
Security Principle
Every client-controlled field, identifier, URL, request, and browser action is untrusted until validated and authorized on the server.
29.1 Input handling requirements
Server-side schema validation
Type validation
Maximum lengths and payload sizes
Unicode normalization where relevant
Output encoding
HTML sanitization only where rich text is intentionally supported
Allowed-protocol validation for URLs
Parameterized database queries / safe ORM patterns
Rate limits on abuse-sensitive endpoints
No executable content in ordinary text fields
29.2 Authorization requirements
Every object-level operation must verify authenticated user -> client account -> ownership/entitlement -> action permission. Hiding a button in the UI is never authorization.
29.3 IDOR/BOLA prevention
Client-supplied website_id, project_id, invoice_id, request_id, domain_id, or subscription_id must never be trusted without a server-side ownership check.

31. Responsive & Accessibility Requirements
31.1 Mobile-first requirement

Final Product Principle
The iDigitalRoot Client Account organizes the client’s relationship with iDigitalRoot and all of their Digital Roots. Each website remains independently manageable through its own CMS, while iDigitalRoot provides the professional service, project lifecycle, commercial control, support, security, and operational continuity around it.
